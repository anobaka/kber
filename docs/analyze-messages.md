# 聊天记录分析文档

## 1. 概述

本文档描述如何将群聊消息和手动添加的知识，通过 LLM 归纳总结后存储到 Milvus 向量库，并实现知识的持续更新与去膨胀。

## 2. 数据来源

知识归纳的原始数据有三个来源：

| 来源 | 表 | 标记字段 |
|------|----|----------|
| 群聊消息 | `chat_message` | `processed = false` |
| 手动添加知识 | `manual_knowledge` | `processed = false` |
| 代码知识 | 由 analyze-repo 流程产出 | 独立流程，见 analyze-repo.md |

## 3. 定时归纳任务

### 3.1 调度策略

- **执行频率**：每 5 分钟一次
- **并发粒度**：以知识库（`kb_id`）为 key，每个知识库独立并发执行
- **防重入**：使用分布式锁（Redis 或 MySQL 行锁），同一知识库同一时刻仅一个任务在执行
- **超时控制**：单个知识库归纳任务超时时间 10 分钟

### 3.2 单次任务执行流程

```
对于每个知识库 kb:
1. 获取锁（lock key = `kb_summarize:{kb_id}`）
2. 查询所有 processed=false 的新数据（chat_message + manual_knowledge）
3. 若无新数据，释放锁，跳过
4. 按时间排序，分批加载（每批 100 条消息）
5. 对每批执行归纳总结（见第4节）
6. 将归纳结果更新到 Milvus
7. 标记原始数据 processed=true
8. 释放锁
```

## 4. 归纳总结策略

### 4.1 核心原则

**增量归纳，而非全量重建**。每次归纳将新消息与已有知识合并、去重、浓缩，避免知识无限膨胀。

**只提取已沉淀的结论，不归纳进行中的讨论**。群聊中的多轮多人讨论往往是渐进式的——有人提出观点、有人反驳、有人补充，最终才形成结论。如果逐条消息归纳，会产生大量中间态、过时甚至矛盾的知识。

### 4.2 话题分组与讨论状态判定

群聊消息在归纳前，需要先进行**话题分组**和**讨论状态判定**，确保只对"已结束"的讨论提取知识。

#### 4.2.1 话题分组（Topic Threading）

将零散的消息聚合为独立的讨论线程：

**分组规则**：
- **时间窗口**：两条消息间隔 ≤ 10 分钟视为同一讨论上下文
- **话题延续**：即使间隔超过 10 分钟，如果后续消息明确引用或回复了之前的消息（飞书回复消息有 `parent_id`），仍归入同一话题
- **话题切换**：当讨论内容发生明显跳转（由 LLM 判定），创建新的话题组

**实现方式**：使用 LLM 对一批消息做话题聚类，Prompt 如下：

```
请将以下群聊消息按讨论话题分组。

## 消息列表
{按时间排序的消息，格式：[时间] 发送者: 内容}

## 要求
1. 将讨论同一话题的消息归为一组
2. 每组输出格式：
   【话题组ID】：{序号}
   【话题摘要】：{一句话描述这组讨论的主题}
   【消息ID列表】：{属于该组的消息ID，逗号分隔}
3. 注意识别多轮讨论中的反驳、补充、修正关系
4. 不相关的独立消息各自成组
```

#### 4.2.2 讨论状态判定

对每个话题组，判定其讨论状态：

| 状态 | 判定条件 | 处理方式 |
|------|----------|----------|
| **已结论** | 讨论有明确结论、决策或共识（如"就这么定了"、"好的用方案A"） | 立即归纳，提取最终结论 |
| **已沉寂** | 话题组最后一条消息距今 > 30 分钟，且无新消息延续 | 归纳时提取讨论中最后的共识或主流观点 |
| **进行中** | 话题组最后一条消息距今 ≤ 30 分钟，且无明确结论 | **暂不归纳**，标记为待定，下次任务再判定 |

**状态判定 Prompt**（对每个话题组调用）：

```
请分析以下群聊讨论的状态。

## 讨论内容
{该话题组的所有消息}

## 最后一条消息时间
{timestamp}（距今 {n} 分钟）

## 请判断
1. 讨论状态：已结论 / 已沉寂 / 进行中
2. 判断依据：{简要说明}
3. 如果是"已结论"或"已沉寂"，提取最终结论/共识：{结论内容}
4. 如果讨论中存在分歧且未解决，标注：存在分歧，各方观点为...
5. 置信度：高 / 中 / 低（对结论确定性的判断）
```

#### 4.2.3 待定消息的处理

- 标记为"进行中"的话题组，其消息**不标记** `processed=true`，保留到下一轮归纳任务
- 在 `chat_message` 表中新增字段 `topic_group_id`，记录消息所属话题组
- 如果一个话题组连续 3 次（15 分钟）被判定为"进行中"，强制将其标记为"已沉寂"进行归纳，避免消息永远积压

### 4.3 归纳流程（单批次）

**步骤一：加载上下文**

从 Milvus 中检索该知识库的现有知识摘要（topK=20），作为历史知识上下文。

**步骤二：消息预处理与话题分组**

1. 过滤无意义消息（纯表情、"好的"、"收到"、"+1" 等短回复，使用停用词表）
2. 对剩余消息执行话题分组（见 4.2.1）
3. 对每个话题组执行讨论状态判定（见 4.2.2）
4. 仅对状态为"已结论"和"已沉寂"的话题组进行归纳

**步骤三：LLM 归纳总结**

对每个可归纳的话题组，调用阿里云百炼 API（minimax-m2.5）：

```
你是一个企业知识库管理专家。你的任务是从群聊讨论中提取确定性的知识。

## 已有知识
{从 Milvus 检索到的相关历史知识摘要}

## 讨论内容
{该话题组的完整消息记录，保留发言人和时序}

## 讨论状态
{已结论 / 已沉寂}
{LLM 判定的结论内容}

## 要求
1. 只提取最终结论和确定性信息，忽略讨论过程中被否定或推翻的中间观点
2. 如果讨论中有明确的决策或共识，以决策/共识为准
3. 如果讨论存在未解决的分歧，将各方观点都记录，并标注"尚有分歧"
4. 与已有知识进行对比：
   - 如果讨论结论推翻了已有知识，生成更新条目（替换旧版本）
   - 如果是全新的知识点，生成新增条目
   - 如果与已有知识一致，则忽略
5. 每条知识以独立段落输出，格式为：
   【主题】：{主题关键词}
   【内容】：{知识内容，简洁准确，100-300字}
   【确定性】：确定 / 有分歧 / 待确认
   【来源】：{参与讨论的人员和群名摘要}
   【操作】：新增 / 更新 / 删除
6. 丢弃闲聊、寒暄、情绪表达等无实质信息的内容
7. 如果讨论中没有任何有价值的知识，回复"无新增知识"
```

**步骤四：解析 LLM 输出**

解析结构化输出，按 `【操作】` 字段处理：

- **新增**：生成 Embedding，插入 Milvus。`【确定性】` 存入 metadata
- **更新**：生成新 Embedding，替换 Milvus 中对应的旧向量（通过主题匹配 + 向量相似度定位）
- **删除**：从 Milvus 中移除对应向量

**确定性标记的作用**：
- RAG 检索时，`确定性=确定` 的知识排序权重最高
- `确定性=有分歧` 的知识在回答时会附带说明"此信息存在不同观点"
- `确定性=待确认` 的知识权重最低，仅在无其他匹配时返回

### 4.4 知识去膨胀机制

为防止知识无限增长，执行以下策略：

**4.4.1 合并相似知识**

每次归纳后，对该知识库执行一次相似度扫描：
- 检索所有知识向量，计算两两余弦相似度
- 相似度 > 0.92 的知识条目标记为候选合并项
- 调用 LLM 将候选项合并为一条更精炼的知识

**4.4.2 知识老化**

- 每条知识记录 `last_referenced_at`（最后被 RAG 检索引用的时间）和 `last_updated_at`
- 超过 90 天未被引用且未更新的知识，标记为"冷知识"
- 冷知识在下一次归纳时由 LLM 判断是否仍有价值，无价值则清除

**4.4.3 容量控制**

- 每个知识库设置软上限（默认 10000 条知识向量）
- 接近上限时，优先合并相似知识、清理冷知识
- 达到硬上限（15000 条）时暂停新增，仅允许更新和删除

## 5. 手动添加知识的处理

当用户通过 `添加知识` 命令提交内容时：

1. 内容保存到 `manual_knowledge` 表
2. **立即触发**一次针对该知识库的归纳任务（不等待 5 分钟定时）
3. 归纳流程与定时任务相同，但仅处理该条手动知识
4. 手动知识的权重高于聊天消息（在 Milvus metadata 中标记 `source=manual`，检索时可加权）

## 6. Milvus 数据结构

Milvus Collection Schema 详见 [schema.md](schema.md) 第 3 节。

每个知识库对应一个 Collection（命名：`kb_{kb_id}`），核心字段包括：`vector`、`topic`、`content`、`source`、`certainty` 等。

### 6.1 Embedding 模型

使用阿里云百炼提供的 Embedding API（或自部署 BGE-M3 模型），保持与 LLM 调用统一的 API 入口，降低运维复杂度。向量维度以实际模型为准，通过配置项 `EMBEDDING_DIM` 指定。

## 7. RAG 检索与回答

### 7.1 检索流程

当用户提问时（自由文本，非命令）：

1. 对用户问题进行 Embedding
2. 在该群绑定的所有知识库 Collection 中并行检索
3. 每个 Collection 返回 topK=10，合并后按相似度重排序，取 top 15
4. 更新命中知识的 `last_referenced_at`

### 7.2 多轮对话上下文

系统在内存中维护每个群聊最近 5 轮的 Q&A 记录，用于支持追问和上下文关联：

- 每次 RAG 回答后，将 `(问题, 回答)` 存入该群的对话历史队列（`deque`，最大 5 轮）
- 下次提问时，历史 Q&A 作为 `## 对话历史` 部分注入 LLM Prompt
- 用户发送 `清空上下文` 命令后，下一次提问不携带历史（一次性生效），之后恢复正常

### 7.3 回答生成

将检索结果和对话历史作为上下文，调用 LLM 生成回答：

```
你是一个企业知识库助手。请根据以下参考资料回答用户的问题。
如果参考资料中没有相关信息，请明确告知用户你无法回答，不要编造答案。

## 参考资料
{知识条目1}
来源：{source_detail}

{知识条目2}
来源：{source_detail}

...

## 对话历史（最近 5 轮，可选）
用户：{历史问题1}
助手：{历史回答1}

用户：{历史问题2}
助手：{历史回答2}

## 用户问题
{用户原始问题}

## 回答要求
- 优先引用参考资料中的信息
- 如果涉及代码，给出具体的文件路径和代码片段
- 回答简洁准确，避免冗长
- 在回答末尾标注主要参考的知识来源
```

回答以飞书 Interactive Card（消息卡片）格式发送，支持 Markdown 渲染。

## 8. 错误处理与监控

### 8.1 LLM 调用容错

- 单次 LLM 调用超时 120 秒（`LLM_TIMEOUT`），重试 3 次（`LLM_MAX_RETRIES`，指数退避 4s/8s/16s）
- 若归纳任务中 LLM 连续失败 3 次，跳过本批次，标记失败原因到日志，下次定时任务重试
- LLM 输出格式解析失败时，将原始输出保存到 `summarize_error_log` 表，人工排查

### 8.2 监控指标

- 每个知识库的知识条目数量（膨胀趋势）
- 归纳任务执行耗时和成功率
- LLM API 调用量和错误率
- Milvus 检索延迟
- 未处理消息积压量（`processed=false` 的数量）
